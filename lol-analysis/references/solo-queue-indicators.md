# 選手公開排位：英雄準備與可比狀態

使用者於 2026-09-20 要求納入 LoL 預測研究。適用新賽前預測；更新沿用仍有效的快照，只補新增對局、帳號或版本資訊。研究優先序為版本相關英雄準備 → 可用替代英雄 → 可比個人表現；總勝率、牌位及連勝連敗只作背景。這是已啟用的研究指標，尚無已驗證的勝率增量，不宣稱加入後已提高命中率。

## 帳號、伺服器與觀察窗口

- 以當場 `confirmed`／`established`／`projected` 先發為母體，兩隊各位置都保留查核結果。有可信輪替情境則分人記錄，不把替補排位移給先發。
- 跟隨選手當時實際使用的伺服器，包括 KR、EUW、NA、可取得的中國伺服器或集訓地；不要依聯賽名稱假定伺服器。多帳號合併前核實歸屬，不因暱稱相似便認定本人。
- 身分以選手／隊伍公開帳號資訊為優先，TrackingThePros、LOLPros 等職業索引作線索並交叉核實；保存證據連結、查核時間、平台、Riot ID，以及可取得的穩定帳號 ID。無可靠交叉佐證標為 tentative，不用它判斷選手；不搜尋未公開的私人帳號。
- 主窗口固定為截止前 14 天，另列最近 7 天的變化；7 天包含於 14 天，不能當兩份獨立證據相加。本人比較基準可用再往前 28 天，即 `[T−42天, T−14天)`，只作狀態背景。版本／位置不相容就分組或記缺比較基準，不為湊量讓舊資料主導。
- 7／14／28 天是第一版研究設定，尚非驗證過的最佳窗口；調整需在看本場結果前記原因與新版本，不能每場挑最支持看法的天數。
- 僅納入截止前已完成、可得的排位單／雙排。補位另列，重開局排除並記原因；特殊模式、彈性排位及公開訓練賽不混進同一母體。同一玩家的同一平台對局 ID 去重，同場多位選手不是彼此獨立樣本。
- 保存每個帳號實際覆蓋的起訖時間、分頁範圍及有效局數。只讀到最近 20 局，不能聲稱已覆蓋 14 天；網頁無資料可能是改名、小號、集訓、抓取受限或沒有公開活動，不推斷沒有練習。

## 指標如何判讀

先從賽前已知的賽事版本、近期正式 BP、對手 ban 與隊伍戰術列出本場相關英雄／功能，再查選手練習；排位熱門不自動等於比賽強勢。保存賽事版本、每局排位版本，以及改動是否影響相關英雄、裝備或功能的理由；不能只因版本號相近便視為相容。

| 指標 | 保存的觀察 | 可以支持的判斷與限制 |
| --- | --- | --- |
| 版本相關英雄準備 | 逐英雄主位置局數、最近使用時間、7／14 天使用占比；相關英雄集合及來源 | 是否有近期練習證據、是否增加符合本場 BP 的選擇。使用占比以有效主位置局數為分母，缺樣本記未知。 |
| 替代英雄準備 | 主力英雄被 ban／Fearless 用掉後，其他相關英雄的局數、對位與表現 | 提出可用替代的假設，再查正式賽能否接上隊伍功能；排位練過不等於已證明 BO5 第四、五套團隊解法。 |
| 可比個人表現 | 按伺服器、版本、英雄、實際位置及對手強度分組；有時間線才列 10／15 分鐘金差、補刀差、經驗差與早期死亡；附每項樣本數 | 比較本人此前相近條件下的變化。打野、輔助按位置解釋，不能拿同一 CS／KDA 門檻評所有人。沒有合適對照就描述原數據，不造「校正後狀態分」。 |
| 背景與覆蓋 | 勝負、勝率、牌位／LP、補位比例、有效局數、可查帳號與時間覆蓋 | 協助解釋樣本，不能直接轉成系列勝率、疲勞、心理或健康判斷。對手當局牌位未知時，今日牌位僅為代理，不冒充當時強度。 |

所有數值帶分子／分母或有效樣本數；區分比賽未達 15 分鐘與時間線缺失，不補零。只取得 KDA／終場數據時不能反推對線金差、失誤原因或團戰品質。跨伺服器分組，不直接比較 KR 與 EUW 的原始勝率或 LP。

小樣本不下強結論；新英雄輸多可能是在學習，連勝也可能來自英雄、對手與隊友組成。對新英雄的練習增量先視為「正在準備」，有可比表現和正式賽機制支持後才能進一步推論。沒有公開練習不證明不會玩；排位無法覆蓋私下訓練賽。

## 接入預測與保存增量

1. 完成正式賽研究與獨立比分基準後，**在讀取本次排位結果之前**，保存未使用排位資訊的 `solo-queue-control-input.json` 和可重播 `solo-queue-control-forecast.json`。此控制版本可使用既有 `analyst_forecast.py build`；對外主預測仍依原流程使用 `build-paired` 產生固定強度影子版本。
2. 兩隊使用同一資料截止與窗口查排位，保存 `solo-queue-evidence.json`。已先看過該窗口排位，或賽後才補資料，明記 `control_blinded=false`／`retrospective`，不回填時間或冒充乾淨前瞻樣本。取得時間、對局發生時間與可得時間分開，資料截止及快照仍依共用契約。
3. 有效來源以 `event.evidence[].kind=solo_queue` 加入，保留標準 `id`、`url`、`claim`、`available_at`、`retrieved_at`、`teams`；`claim` 說明選手、窗口、版本、樣本及發現，原始明細留附件。這類來源不計作正式賽 `match_detail`。
4. 逐項裁決為 `supports`、`contradicts`、`mixed` 或 `unknown`，並記 `usage=analyst_parameter_basis|unquantified_context|not_used`。若影響分析者情境，在 `evidence_ids`／`counterevidence_ids` 引用，說明哪個 BP／對位機制、哪個情境權重或條件率受影響，以及幅度為主觀估計的理由。不能按排位勝率、練習局數或連勝自動加固定百分點，也不能與正式賽英雄池證據重複加分。
5. 保存加入排位後的主輸入與完整主分布，另在 `solo-queue-impact.json` 記兩版路徑／forecast ID、真正建立時間、控制版本是否未看排位、哪些證據改變哪些參數、勝率及方向差異。未改判也保留數值對照與理由；資料缺漏保留在覆蓋分母。除排位相關證據與有理由的參數變更外，保持正式賽資料、隊序、截止與計算方法相同；有其他更新就標為混合變更，不歸因於排位。

以上立即啟用的是使用者要求的領域研究及實驗情境依據。沿用既有「分析者情境估計／未實證校準」標示；正式模型沒有此特徵時，只保存獨立挑戰版或未量化背景，不手改正式模型輸出。候選資格限制新增已驗證數值效果，不將使用者要求的研究停用；若已影響對外實驗情境，須如實記錄，不能以 registry 的 `used_for_prediction=false` 宣稱從未使用。

## 每場最小紀錄

`solo-queue-evidence.json` 是人工研究附件，沿用當次 run 目錄；目前沒有專用自動抓取器或語意驗證器，不能把 forecast CLI 通過當成帳號與內容已核實。

| 層級 | 欄位／內容 |
| --- | --- |
| 事件 | `method_version=lol-soloqueue-research-v1`、`event_id`、`data_cutoff`、`created_at`、窗口界限、賽事版本與來源、`mode=prospective|retrospective` |
| 選手 | 隊伍、選手、先發分類、位置、已核實／tentative 帳號、實際伺服器、身分來源、`coverage=complete|partial|unavailable` 及具體理由；complete 僅指已知公開帳號的窗口 |
| 對局 | 帳號／平台對局 ID、時間、版本、英雄、實際位置、勝負、來源與查核時間；可取得的時間線欄位，納入／排除理由 |
| 指標 | 7／14 天分組樣本、本人比較基準、版本相關英雄集合／來源、英雄準備與可比表現、支持與反證；缺值及原因 |
| 使用 | 逐項裁決、實際用途、受影響情境／參數、未採用原因、`solo-queue-impact.json` 定位 |

正文只將影響方向的觀察整合進既有分析段，例如「版本相關替代角已有近期練習，但對本對手的團隊執行仍未驗證」；不新增十人戰績表到聊天模板，不把品質分數改成命中率。

## 回收與候選狀態

在既有 factor registry 分別追蹤 `soloqueue-patch-champion-readiness` 與 `soloqueue-role-adjusted-form`，初始為 candidate、前瞻配對 0。分開記研究已啟用、是否影響已發布實驗情境、是否已有固定數值映射；本次沒有實作或驗證自動勝率係數。

回收整批加入前後的同事件結果：勝方、精確比分、Brier、log loss 及資料／預測覆蓋；依賽區、版本可比性、英雄準備與狀態分組，包含未改判與失敗例子。英雄選用能否預先提示與比賽勝方能否預測分開評估；前者命中不能冒充後者改善。手動調整情境的對照評估的是整個判斷程序，不能宣稱某一欄的因果效果。

升版仍依 `systematic-validation.md` 與共用 postmortem 契約。已有固定強度影子版本和這項排位對照分開保存，不能逐場挑算對的版本。已看過結果的昨天比賽只可作開發研究，不能補造排位前瞻成績。
